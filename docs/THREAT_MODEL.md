# OpenRamp: Threat Model

Status: v0.4 (Nov 3, 2026). v0.2 added T23–T30 (D-009); v0.3 T31 (D-012), T32, no owner (D-014); v0.4 T33–T36 and the Q5 recipient check (D-016 to D-018). Rule: no defence may rely on an admin or arbiter.
Each row maps to a test (filled in as tests are written).

| # | Attacker | Attack | Defence | Test |
|---|---|---|---|---|
| T1 | Buyer | Fake receipt / screenshot | The contract never trusts user evidence; only the verifier's Paystack lookup with the LP's key counts | — |
| T2 | Buyer | Reuse one real payment for two orders (replay) | Reference is `opr-<deploy_tag>-<order_id>`, issued by the contract (unique across deployments, T27); verifier checks the reference matches; contract records used references and rejects a second use | — |
| T3 | Buyer | Pay a smaller amount, or in another currency | Verifier checks amount ≥ expected and currency = GHS | paystack-verify `short_amount_is_not_paid`, `wrong_currency_is_not_paid` + live run (M0.5) |
| T4 | Buyer | Pay after the deadline, then claim | Verifier checks `paid_at ≤ pay_deadline`; late payments are refunded off-chain by the LP (out of scope) | paystack-verify `late_is_not_paid` + live run (M0.5) |
| T5 | Buyer | Claim during a Paystack outage hoping to slash the LP without paying | Outage gives UNVERIFIABLE, not PAID. Outage results are class `OUTAGE`, so a slash needs `min_failed_attempts` failures spanning `T_outage_max` (72 h in prod), not `T_retry` (D-012); anyone, including the LP, can re-claim during that window so a real outage clears. Each claim costs the OutLayer fee | — |
| T6 | Buyer | MoMo reversal after receiving USDC | New-buyer amount cap and `release_delay`; residual risk accepted by LPs and stated in README | — |
| T7 | Buyer | Open many orders without paying to lock LP liquidity (griefing) | Orders expire after `T_pay + T_grace`; new-buyer cap and exposure limit; buyer pays non-refunded storage per order. Residual: an experienced buyer can still lock up to `max_usdc` per order for 45 min; a small order fee / per-buyer open-order limit is PLAN M1.10 [nice] | escrow `expire_after_grace_unlocks_everything`, `new_buyer_order_above_cap_fails` |
| T8 | LP | Receive cedis, then revoke/rotate the Paystack key so verification fails | Revocation → UNVERIFIABLE → after `T_retry` the bond pays the buyer in full (bond rule `open_buy_notional ≤ bond`) | live run with invalid key → UNVERIFIABLE `auth_error` (M0.5); slash test in M1.6 |
| T9 | LP | Withdraw bond or change `secret_ref` while orders are open | Contract blocks both while the LP has any open order. Changing the key *inside* the secret is T24 | escrow `set_secret_ref_with_open_order_fails`, `withdraw_bond_with_real_open_order_fails` |
| T10 | LP | Change the rate after the buyer opened the order | Rate and `ghs_amount` are fixed in the order at open time | escrow `rate_change_after_open_does_not_change_the_order`; buyers may cap the amount before open: `rate_raised_before_open_is_caught_by_the_buyers_maximum` |
| T11 | LP | Never pay out in a sell order but keep the seller's USDC | USDC only goes to the LP on PAID or seller confirmation; otherwise the seller refunds after the deadline | — |
| T12 | Seller | Receive cedis, then refuse to confirm | The LP proves the payout with `claim_payout`; the verdict releases USDC without the seller | — |
| T13 | Outsider | Call the callback directly with a fake PAID | Callback is `#[private]` (only the contract's own `.then` can deliver it) and must match the order's current request id. Confirmed in Test A (M0.4): direct call → "Method on_result is private" | test-a `on_result` (testnet); escrow test TBD |
| T14 | Outsider | Front-run: see a buyer's payment reference and claim it for their own order | Reference is tied to one order id; claiming another order with it fails the reference check | — |
| T15 | Anyone | Two claims in flight; callbacks arrive out of order | One verification in flight per order; stale callbacks ignored | — |
| T16 | OutLayer | Never responds / errors | Yield timeout or error → UNVERIFIED (never NOT_PAID, never release); retry allowed. Test A: failed run returns JSON `null`; OutLayer's timeout path returns no value (empty); oversized result → treat as no value | test-a `classify` unit tests |
| T17 | OutLayer/TEE | Compromised worker returns a false PAID | Trust assumption of the design (TEE attestation by OutLayer). Documented in README as a limitation | — |
| T18 | Anyone | Storage exhaustion by creating many orders | Caller pays storage for each order, including room for what later steps write (D-020); kept for the order history, not refunded; per-account indexes cost O(1) per order | escrow `register_without_storage_deposit_fails`, `storage_charge_is_exactly_written_bytes_plus_reserved_growth`, `storage_deposit_one_yocto_short_fails`, `cost_per_order_does_not_grow_with_history` |
| T19 | Anyone | Leak phone numbers or keys | Phone numbers only on Paystack pages / LP service; keys only in OutLayer secrets, bound to the verifier wasm hash and readable only via the escrow (`--access allow-all --via <escrow>`); verifier prints only verdict/reference/reason; review prompt checks logs | M0.5: direct call to the LP's secret refused ("Access denied"); escrow `register_emits_event_without_secret_profile` (by value) |
| T21 | Anyone | Trigger verification with their own wasm that always prints PAID | The escrow fixes the verifier source (wasm URL + sha256, or OutLayer project + version) at deploy; callers can never choose it. Found in Test A: the probe's `request()` takes the URL from the caller, the escrow must not | — |
| T22 | OutLayer operator | The OutLayer operator account submits a false result (`resolve_execution` is operator-only) | Same trust assumption as T17 (TEE attestation); documented in README | — |
| T20 | Deployer | Change parameters to trap open orders | There is no owner role and no setter: all parameters are fixed at init (D-014). Orders still copy the parameters they were opened with | escrow `init_stores_fixed_config` (no setter exists to test) |
| T23 | LP | Sell order: send the "payout" with the right reference and amount to the LP's own second wallet, get PAID, keep the seller's USDC | Seller commits `sha256("openramp-sell-v1|" + salt + "|" + number + "|" + provider)` at open; the salt reaches the verifier only as the payout's single pawaPay metadata field; the verifier recomputes the hash from pawaPay's recipient phone + provider; mismatch, missing or extra metadata = NOT_PAID; each payoutId settles one order (SPEC §5, inv. 13, D-018) | — |
| T24 | LP | Buy order: take the buyer's money on Paystack account A but verify with a key for account B (or swap the key inside the secret), so the lookup says "not found" → NOT_PAID → order expires, LP keeps the cedis | `key_fp = sha256(key)` recorded by the TEE at registration; every verdict carries it, mismatch = UNVERIFIABLE → slash; the checkout is created inside the TEE with the same key (SPEC §3, §4, inv. 10) | — |
| T25 | Buyer | Make verification fail on purpose (too little deposit/gas, bad limits) so failures pile up and the LP gets slashed without the buyer paying | Contract sets deposit, gas and limits itself; slash needs `min_failed_attempts` failures spanning `T_retry` (LP_FAULT) or `T_outage_max` (outage only) (inv. 11, D-012) | — |
| T26 | Deployer | Swap the verifier for one that always says PAID, swap the token for a fake one, or redeploy the contract code | Verifier, token and OutLayer id fixed at init with no setter; `ft_on_transfer` checks the token; no full-access key on the contract, or the upgrade trust is stated in the README (inv. 9) | escrow `deposit_from_other_token_fails`, `deposit_called_directly_by_lp_fails` (token check); no-setter tests in M1.9 |
| T27 | Buyer | Replay an old successful `opr-1` against a new deployment's order 1 (order ids restart), or across two instances sharing one Paystack account | `deploy_tag` = first 8 hex of `sha256(contract_id ":" init_block_height)` in every reference (inv. 12) | escrow `deploy_tag_is_8_hex_and_differs_per_deployment`, `deploy_tag_matches_spec_formula` |
| T28 | Anyone | Keep reopening orders against an LP so it never reaches zero open orders and can never withdraw its bond or rotate a leaked key | `pause_lp()` blocks new orders so the LP can drain to zero (inv. 14) | escrow `paused_lp_cannot_lock_new_orders`, `paused_lp_can_still_close_open_orders_and_resume` (internal helper); escrow `open_with_paused_lp_fails` |
| T29 | Buyer | Bypass the per-account new-buyer cap with many free NEAR accounts (reversal fraud) | Per-LP `new_buyer_exposure_max`, set by the LP (inv. 14); new-buyer status counted per (lp, buyer), so another (colluding) LP cannot graduate a buyer (D-020) | escrow `many_new_buyers_hit_the_lp_exposure_limit`, `new_buyer_exposure_at_exactly_the_limit_is_allowed`, `history_with_one_lp_does_not_make_a_buyer_experienced_with_another` |
| T30 | LP | Make runs fail on purpose (delete the secret, change its access rule) so failures never count against it | The contract only sees `null` and cannot tell who caused a failure, so every failure counts as UNVERIFIED and ends in a slash after the retry window (fails closed) (SPEC §4.5, inv. 11) | — |
| T31 | Provider / OutLayer outage | A long Paystack, pawaPay or OutLayer outage makes an honest LP's checks fail, and the LP is slashed although the buyer never paid | Failures are classed (SPEC §4.5): outage-only streaks get `T_outage_max` (72 h) instead of `T_retry` (24 h), and any successful re-check (PAID or NOT_PAID) ends the streak. Still ends in a slash at the hard limit, because an LP-caused `null` looks the same as an outage (T30). Residual risk: an outage longer than 72 h on an unpaid order; accepted and stated in the README (D-012) | — |
| T32 | Anyone | Front-run the deploy: call `new` on our freshly deployed contract with their own verifier (one that always says PAID) or token | `new` requires predecessor = the contract account; deploy and `new` go in one batched transaction (inv. 9, PLAN M2.7) | escrow `init_by_another_account_is_rejected` |
| T33 | LP | Register with another LP's OutLayer secret (`secret_ref` naming someone else's account), so the verifier uses that LP's Paystack key for the attacker's orders | `register_lp` requires `secret_ref.account_id` = the registering LP (SPEC §3.1) | escrow `register_with_someone_elses_secret_fails` |
| T34 | Anyone with a leaked LP function-call key (e.g. from the web app's wallet login) | Reprice the LP's quote (rate ≈ 0), then open buy orders and pay pennies for its USDC | `update_quote` and every LP setting require exactly 1 yoctoNEAR, which a function-call key cannot attach (D-016) | escrow `update_quote_without_one_yocto_fails`, `set_secret_ref_without_one_yocto_fails`, `pause_without_one_yocto_fails` |
| T35 | LP or anyone | Buy order: claim while the buyer's MoMo charge is still pending (she approved late on her phone), get NOT_PAID after the deadline, order expires; the money then settles to the LP and the buyer has no remedy | Pending charges are `PENDING` = `OUTAGE`, never NOT_PAID; the order stays UNVERIFIED and re-claimable, ending in PAID or a slash at `T_outage_max` (SPEC §4.4, D-017) | — |
| T36 | Seller | Sell order: refund while the LP's payout is still in flight (ACCEPTED / PROCESSING), keeping the USDC and then also receiving the cedis | pawaPay pending states are `PENDING` = `OUTAGE`, so the refund window is `T_outage_max`, and a later COMPLETED proves the payout (SPEC §5, D-017) | — |
